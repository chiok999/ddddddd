# Provider follow-up audit

This audit is based on code and offline fixtures. The user supplied independent upstream observations; this environment did not verify those providers or Botkeep playback. No provider is permanent, and successful metadata is not proof a stream works or survives signed-URL expiry.

## Confirmed and changed

- `providers.js`: VaPlayer and VidSrc labeled all results HLS, while `movy.js` did likewise. Explicit `.mp4`/`.m4v` paths are now classified as file; explicit `.m3u8` and unknown opaque paths remain HLS. VidSrc extraction accepts explicit MP4 paths as well as HLS. Extension classification does not verify actual content, fast-start layout, authorization, or CDN reachability; the MP4 gate remains authoritative.
- `providers.js` previously awaited every adapter beyond each underlying call's timeout. Independent 6/10/12-second budgets now abort production `providerRequest` fetches. An adapter that ignores its signal can still continue in the background; synchronous QuickJS work can block the event loop. Budgets may exclude slow but working results. Forced re-resolution invokes only its original adapter. Movy skips its ten-minute result cache when explicitly refreshed.
- Identical URLs are removed only when format and effective referer/origin/user-agent match; otherwise alternatives are retained because header differences can determine whether a CDN accepts them. Session-only client ordering considers actual `playing` events and exhausted attempts, not imagined availability. It resets on reload and does not prove long-term reliability.
- VidLink parses a positive plausible upstream `stream.TTL` and requests re-resolution at 75% of that value, capped at 45 minutes, on a later source open. The six-hour session-bound handle lifetime is not proof of the CDN signature lifetime. If a refreshed object is ambiguous or has a different validator, a range splice fails closed; the app cannot guarantee refresh success.
- `network.js` strips authorization, proxy authorization and cookies after a cross-origin redirect. HTTPS and public-IP DNS checks still run on each hop. Provider API response bodies remain capped at 2 MiB, while media is streamed rather than buffered under that cap.
- `login-limiter.js` isolates immediate-peer buckets (eight failures/minute), with a 120/minute global backstop. Untrusted forwarded headers are deliberately ignored. If all users reach the service through one reverse proxy, their bucket is shared; a distributed attack can still trigger the global backstop.
- `source-store.js` replaces the prior restart-required source handle threshold with 2,000 least-recently-used handles per session and 12,000 globally. This is a handle-count bound, **not a conversion-output size or free-space cap**. Eviction can invalidate an unstarted alternate; active conversions retain their source object.
- `kisskh.js` caches episode details for two minutes; unsuccessful lookups are not cached. `movy.js` reports malformed embedded detail JSON as an explicit provider error. `public/app.js` reports HTTP status when a response is not JSON.
- `playlist.js` had no production callers (`rg` found only its unit test); it and that test were removed. HLS conversion is not implemented, and removing this unused rewriter does not enable it.

## Findings corrected or still open

- The reported 1 GiB limit is no longer present in `transcode.js`: PR #42 removed it and the free-space reserve. Real filesystem or host quotas can still fill.
- `server.js` rejects HLS as an input. Extension recognition does not make actual HLS playable. Non-fast-start MP4 and metadata over 8 MiB remain unsupported. FFmpeg still reads from a non-seekable pipe, and a seek can discard the old job before its replacement works.
- FFmpeg is killed and its output deleted when a job is explicitly stopped; a graceful HLS ENDLIST would not preserve that output under the current lifecycle. PID-based crash cleanup can miss directories after PID reuse. Neither behavior was changed.
- MovieBox already retries the returned player domain after empty responses or 403/404 and refreshes its token on 401. No claim that two tokens remain valid simultaneously is established; background token warming was not added. KissKh still uses the bounded QuickJS execution and fixed token function/version; it can break when the provider changes. A persistent last-known-good script was not added because successful local evaluation is not proof that an old script remains safe or valid.
- Movy intentionally serializes requests and applies a 12-second overall deadline and rate-limit cooldown; it may not reach every server. The provider deadline does not make an unavailable source reliable. No origin health timer was added, since metadata health is not media health and recurring probes can contribute to throttling.
- The original bot's downloader and its previously documented SSRF exposure are outside this standalone app and were not changed.
