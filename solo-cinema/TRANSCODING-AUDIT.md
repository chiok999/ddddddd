# On-demand transcoding audit

- `transcode.js`: a single job reads a session-bound source through the existing pinned HTTPS fetcher. Only fast-start MP4 is accepted; the gate rejects media-first, oversized metadata and non-MP4 input before consuming the whole file. FFmpeg receives stdin, with its input format fixed to MOV/MP4 and its protocol whitelist restricted to `pipe`. No shell, remote URL, user-derived arguments, arbitrary output path or provider headers are passed to FFmpeg. This reduces SSRF exposure but does not sandbox FFmpeg's native media decoders; run an updated build as an unprivileged user in an isolated container.
- `server.js`: transcode start and stop require login and same-origin POSTs; source handles and generated output are bound to the session. Output paths are restricted to the two generated playlists and numeric TS files. Missing, expired, foreign, HLS, oversized and traversal paths are rejected. The existing bot downloader is not exposed.
- Resource limits: one server-wide job; two H.264/AAC encodes; FFmpeg is killed on stop/error/timeout, 90-second inactivity, or output above 128 MiB as observed by the two-second monitor. Monitor-based disk limiting is not a hard filesystem quota. Shutdown requests cleanup; a crash may leave files that a later startup reaps after the age threshold if the PID is gone. FFmpeg is not bundled and needs an up-to-date installation with libx264 and AAC. CPU/load and filesystem quota on Botkeep are unknown.
- Playback: the output is a short live HLS window, not a complete VOD transcode. Seeking beyond retained segments and regular resume are unavailable, long pauses can fall outside the window, playback starts from zero, and only the first audio track is encoded. HLS-only sources, MP4s with trailing `moov`, and media needing FFmpeg network/file protocols cannot be converted. A smaller input may be upscaled; no detail is created. Higher original qualities require switching back to the original source. These restrictions are deliberate and surfaced in the README/UI.
- Testing in this environment: synthetic fast-start MP4 with video/audio was read as a stream and FFmpeg encoded both variants; each generated TS segment was then decoded with video and audio mappings. A silent MP4 was encoded, a one-byte output limit stopped its job, and tests covered session isolation, concurrent-job rejection, missing FFmpeg, HLS rejection, unsafe input gating, stop/cleanup and simulated UI switching. FFmpeg integration test is opt-in through `CINEMA_TEST_FFMPEG`; the locally downloaded older static binary was used only for testing, not bundled or recommended for deployment. A real browser, live provider source, Botkeep performance, privacy isolation and long-duration playback were not verified.
