# On-demand transcoding audit

- `transcode.js`: a single job reads a session-bound source through the existing pinned HTTPS fetcher. Only fast-start MP4 is accepted; the gate rejects media-first, oversized metadata and non-MP4 input before consuming the whole file. FFmpeg receives stdin, with its input format fixed to MOV/MP4 and its protocol whitelist restricted to `pipe`. No shell, remote URL, user-derived arguments, arbitrary output path or provider headers are passed to FFmpeg. This reduces SSRF exposure but does not sandbox FFmpeg's native media decoders; run an updated build as an unprivileged user in an isolated container.
- `server.js`: transcode start and stop require login and same-origin POSTs; source handles and generated output are bound to the session. Output paths are restricted to the two generated playlists and numeric TS files. Missing, expired, foreign, HLS, oversized and traversal paths are rejected. The existing bot downloader is not exposed.
- Resource limits: one server-wide job; two H.264/AAC encodes; FFmpeg is killed on stop/error/timeout, 90-second inactivity, or output above 128 MiB as observed by the two-second monitor. Monitor-based disk limiting is not a hard filesystem quota. Shutdown requests cleanup; a crash may leave files that a later startup reaps after the age threshold if the PID is gone. A pinned platform-specific FFmpeg is installed as an optional npm package for Linux x64 and ARM64 (glibc/musl); a working system binary is the fallback. An explicit `CINEMA_FFMPEG` overrides both. Linux x64 packaged binaries are approximately 83 MiB each; `npm ci` in this environment installed both glibc and musl (about 166 MiB total), and dependencies include GPL-3.0-or-later and FDK-AAC licensing. Keep it updated; native media decoding is not sandboxed. CPU/load and filesystem quota on Botkeep are unknown.
- Playback: the output is a short live HLS window, not a complete VOD transcode. Seeking beyond retained segments and regular resume are unavailable, long pauses can fall outside the window, playback starts from zero, and only the first audio track is encoded. HLS-only sources, MP4s with trailing `moov`, and media needing FFmpeg network/file protocols cannot be converted. A smaller input may be upscaled; no detail is created. Direct playback is disabled; unsupported inputs now fail instead of falling back to the original. These restrictions are deliberate and surfaced in the README/UI.
- Testing in this environment: synthetic fast-start MP4 with video/audio was read as a stream and FFmpeg encoded both variants; each generated TS segment was then decoded with video and audio mappings. A silent MP4 was encoded, a one-byte output limit stopped its job, and tests covered session isolation, concurrent-job rejection, missing FFmpeg, HLS rejection, unsafe input gating, stop/cleanup and simulated UI switching (older direct-play fixtures require updating). The integration test automatically uses the installed bundled binary, or a `CINEMA_TEST_FFMPEG` override. Tested the Linux x64 glibc packaged FFmpeg 8.1.3; ARM64 and musl builds were not run. A real browser, live provider source, Botkeep performance, privacy isolation and long-duration playback were not verified.

- Screenshot diagnosis: the former code mapped **every** subprocess spawn error to the same message, so the screenshot alone cannot distinguish a missing executable from a permission, loader or other spawn error. Troy now probes execution and the required encoders, muxer and filters before fetching video, attempts a packaged binary then a system binary, and reports missing-loader and permission failures separately. If npm omits the optional dependency or the filesystem prevents execution, transcoding can still fail; neither Botkeep architecture nor installation has been inspected.


## EVENT output update

- `transcode.js` now emits growing EVENT playlists with all produced segments retained; normal completion includes ENDLIST. The session remains bound to its owner and is cleaned on stop, timeout and errors. HLS.js requests the start of the event rather than starting at the live edge. Native-HLS quality changes attempt to retain the current position. No unconverted future segments are fabricated.
- The output monitor defaults to 1 GiB across both encodes and stops the job if less than 256 MiB is free on the temp filesystem. Measurements run every two seconds and are not a hard quota. Monitored capacity may be exceeded between checks, so deploy with a filesystem quota if necessary. When a known conversion failure occurs, its message is available briefly to the same session; the browser uses it when playback fails.
- A real synthetic 44-second MP4 was streamed to the actual `createTranscoder` job: both output manifests retained more than eight segments, still exposed their first segments, and had ENDLIST at completion. First and last segments of both outputs were decoded with video and audio. Cross-session reads failed. A one-byte output threshold test confirms cleanup and same-session failure status. Simulated UI tests cover HLS configuration and native quality position restoration; no actual browser, live provider, 1 GiB saturation, long-pause, or Botkeep test was performed.


## Restart at a timestamp

- The bounded fast-start metadata gate parses MP4 `mvhd` versions 0/1 for a finite positive duration no longer than 24 hours. It rejects a nonzero offset when the duration is missing or the requested offset is outside it. Offsets are finite and capped at 24 hours; session/source ownership and same-origin authentication remain required. The gate still restricts FFmpeg to pipe input and MOV demuxing, and validates `moov` before forwarding bytes; no external downloader or FFmpeg network protocol is enabled.
- Seeking within a current EVENT uses browser seeking; a seek outside it cancels the old job, deletes its temporary output and starts another input-side `-ss` conversion with a burst read. The custom controls display source duration and add the seek base to the local media time. Request IDs allow cancellation of an in-flight job, restricted to the owning session; the client serializes replacement jobs and discards stale replies. Uploaded/provider subtitle cues are shifted by the base when supported by browser cue APIs.
- A pipe is not byte-seekable. This approach may need to consume the original bytes from the beginning up to the target, so late seeks can be slow and expensive in upstream traffic. It is not equivalent to a local seekable file or validated remote range access. Seeking can fail on unsupported MP4 layouts, signed/expired provider links, insufficient space, slow sources, or when the three-minute seek startup deadline is exceeded. The original is never delivered directly. Long videos may still exceed the 1 GiB retained-output cap; HLS and other source formats are unsupported.
- A real FFmpeg integration test used a 20-second red-then-blue MP4 and sought to 12 seconds before any previous conversion: the generated 240p output decoded to blue, and the duration returned was 20 seconds. Tests also cover owner-only cancellation, rapid superseding seeks, duration parsing, simulated full-timeline UI and uploaded-cue shifting. They do not establish real browser timestamps, mobile subtitle behavior, live provider latency or Botkeep resource use.
