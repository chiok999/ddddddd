# Full-length seeking and mandatory transcoding investigation

**Status:** mandatory conversion was added after this investigation; full-length VOD seeking remains unimplemented. The transcoder is still a rolling live HLS window.

## Confirmed trigger

- `transcode.js` encodes the input into HLS with `-hls_list_size 8` and `delete_segments`; it does not generate a full VOD playlist or pass original duration to the player.
- `public/player-ui.js` takes the progress bar's length from `video.duration`, which for this rolling playlist reflects the current live timeline rather than the full source duration. Seeking beyond segments still in the window cannot work. The screenshot showing 0:49 / 1:04 and the live-conversion notice is consistent with that behavior, not the episode's length.
- `server.js` rejects `entry.format==='hls'` in `/api/transcode`; `transcode.js` admits only fast-start MP4 and pipes its bytes to FFmpeg with `-protocol_whitelist pipe`. The current system cannot safely enforce conversion of *all* existing streams without making HLS-only and non-fast-start sources unavailable.

## Tested locally

Using the installed FFmpeg 8.1.3 binary, a synthetic 20-second fast-start MP4 containing 10 seconds of red followed by 10 seconds of blue was piped to FFmpeg. Output-side `-ss 12` produced blue pixels, proving FFmpeg can discard the beginning and produce the requested content from a pipe. The automated test `FFmpeg can discard to a later MP4 timestamp on a pipe` reproduces this. This is **not** efficient random access: a pipe cannot seek by HTTP Range, and FFmpeg must consume the stream up to the requested time. Latency, upstream bandwidth, FFmpeg read-rate pacing, subtitle timing, cancellation and late-film behavior have not been established. This test does not implement seeking in Troy.

A synthetic HLS playlist referencing `http://127.0.0.1:9999/segment.ts`, sent to FFmpeg with `-protocol_whitelist pipe`, failed with `Protocol 'http' not on whitelist 'pipe'!` and exit status 183. This is the intended security boundary: enabling FFmpeg's network protocols or giving it provider-controlled playlists without strict mediation can reintroduce server-side access to private addresses and arbitrary URLs.

## Supplied upstreams

- [ErsatzTV Next](https://github.com/ErsatzTV/next) is a scheduled live-channel engine and requires its own patched FFmpeg build. Its `crates/ffpipeline/src/keyframe_seek.rs` explicitly handles keyframe landing and timestamp correction for stream-copy playouts; it does not by itself provide Troy with a secure random-access VOD service.
- [MediaCMS](https://github.com/mediacms-io/mediacms) documents chunked transcoding and HLS, but is a full upload/encode CMS with Django, Celery, Redis and PostgreSQL. Its README suggests 4 GB RAM and substantial storage for its target deployments. Its workflow is not a drop-in for this 2 GB streaming-only project.
- [go2rtc](https://github.com/AlexxIT/go2rtc) documents FFmpeg-backed HLS inputs and on-demand producers, but its HLS output documentation describes live streaming and says its implementation may not work with all players. Its README warns that access to its API can permit command execution. Pointing it directly at provider URLs would bypass Troy's existing DNS-pinned HTTPS checks; its documented live output alone does not establish full-duration VOD seeking.
- [MediaMTX](https://github.com/bluenviron/mediamtx), [SRS](https://github.com/ossrs/srs), [Restreamer](https://github.com/datarhei/restreamer) and [Ant Media Server](https://github.com/ant-media/Ant-Media-Server) primarily provide live streaming infrastructure; their existence does not demonstrate session-bound seekable VOD or safe provider URL handling in this deployment.

## Remaining work

A complete implementation needs session-bound source duration and full-timeline seek semantics, a secure seekable/range-aware source adapter for MP4, a separately validated HLS VOD adapter for playlists, segments and encryption, cancellation/cleanup, subtitle synchronization and automatic conversion of every playable result with no direct-play fallback. Unsupported or unsafe inputs must fail explicitly. Changing the browser's displayed duration without supplying seekable media would be misleading. These behaviors, long-video resource usage and Botkeep playback have not been implemented or verified here.

## Mandatory conversion update

Automatic conversion and blocking original media playback were subsequently implemented. The remainder of this report still applies: HLS inputs and full-timeline seeking are not implemented. The focused conversion, fail-closed, stale-job and HTTP tests passed, along with the real synthetic FFmpeg integration. The full suite currently has 13 failing simulated UI tests; many still mock direct playback rather than a successful transcode and include obsolete direct-quality expectations. These failures have not been fully audited, so they cannot be dismissed as fixture-only or taken as proof the remaining UI is healthy. Real-browser and Botkeep playback have not been verified.

## Range and harvest follow-up

The supplied plan correctly distinguishes a seekable local file from stdin. A local synthetic fast-start MP4 containing red followed by blue was successfully decoded at 12 seconds using input-side `-ss` against the file. This does not measure real-provider latency, prove that remote MP4 supports ranges, or implement a seekable source in Troy. Input-side `-ss` with `-noaccurate_seek` may land early; `-copyts -start_at_zero` alone does not establish a full original-duration browser timeline.

The MovieBox home response fetched in this environment included a movie with `duration: 5940` and series entries with `duration: 0`; title-level metadata is not reliable evidence of a specific episode's runtime. The existing MovieBox play adapter was already inspecting `stream.duration` to reject short clips, but discarded it. It now retains a finite positive duration of at most 24 hours on the individual MP4 stream and includes it in the authenticated resolve result. This value is provider metadata, not a verified timeline; it is not used to manufacture a playlist or seek bar.

A session-bound `POST /api/source/probe` accepts an existing `/media/` handle, not a URL. It tests two-byte GET ranges at byte zero and halfway through a progressive source through the same HTTPS/redirect/public-DNS checks as the transcoder. It cancels both bodies and requires consistent valid 206 Content-Range headers; it returns status and size, not signed URLs. It refuses declared HLS inputs, caps concurrent probes to two, and times out. A positive result verifies compliant headers at two offsets only, not that the bytes are truthful, stable across token expiry, or that FFmpeg can efficiently seek and decode the source. The API is diagnostic and is not wired into playback or exposed as a user control. Tests cover successful ranges, 200 range-ignoring origins, inconsistent size, bad headers, encoding, authentication and session ownership.

**Actual provider go/no-go:** the available web fetch returned MovieBox player domain `mzfi.me`, but unauthenticated `subject/play` requests for The Beast and The Rings of Power S1E1 returned empty `streams`, `hls` and `dash` arrays with `hasResource:false`. No signed episode media URL or playlist was obtained. This environment's command-line outbound network only allows selected package/GitHub hosts, so the requested episode Range and out-of-window segment probes could not be performed. These results do not establish what Botkeep's guest session or region receives. No speculative URL parameters, filename arithmetic, mobile endpoint, token scope or segment duration was assumed to work.

N_m3u8DL-RE documents live capture, but its real-time merge is container/setting dependent; its default also retains segments. yt-dlp documents `--live-from-start` as experimental and supported only on YouTube, Twitch, TVer and mellow-fan. No integration was added: letting any of these tools independently fetch provider-controlled URLs or playlists would bypass the public-DNS and redirect controls. They also write growing files and do not make unharvested content seekable. A fabricated VOD playlist is unsafe unless real segment boundaries, durations, discontinuities, encryption, byte ranges and complete mapping are actually known; using a larger EXTINF while returning just one segment would report false timestamps and omit content.

Changing the rolling 32-second output to unlimited EVENT without a storage strategy is not safe for the existing 2 GB deployment. At the configured nominal 250k+48k and 600k+64k bitrates, both outputs total approximately 433 MB/hour before HLS overhead and metadata; the existing 128 MiB monitor would stop a long episode after a fraction of its runtime. No EVENT harvest, reuse cache, HLS input, full-duration scrubber, arbitrary seek, or original-source fallback was introduced by this follow-up. A strict filesystem quota is still necessary to enforce a hard ceiling; the existing monitor checks periodically.
